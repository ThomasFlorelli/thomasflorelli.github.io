00

Reviewing isn't hunting for mistakes

A review that just flags style nits delivers the value of a linter — which is to say, almost nothing, since the linter does it for free. A reviewer's value lies elsewhere: understanding the intent, judging whether the change actually solves the problem, and anticipating what will break six months from now.

The reflex to build: before judging the "how," reconstruct the "why." A PR is a hypothesis — "this code solves this need without breaking anything." Your job is to test that hypothesis, not to rewrite the code in the author's place.

Guiding principle

You're approving an intent, an approach, and a slice of technical debt — not just lines. Always ask: "if this code blows up in production three months from now, would I have seen it coming here?"

01

The process, step by step

A deliberate reading order avoids the classic trap: drowning in the first file you open and losing the big picture. Move from context to detail.

  1. Read the description before the code

    What problem? Which ticket? What's the stated approach? If the description is empty or vague, that's already a review comment to write — you can't validate what you don't understand.

    Why: without a clear intent, every line becomes ambiguous. You then judge the code against your idea of the need — the #1 source of pointless reviews.

  2. Frame the scope and the risk

    How many files, which areas? Does it touch authz, migrations, payments, a public API? A 3-line change in the auth layer deserves more attention than 300 lines of tests. Calibrate effort to risk, not to volume.

    Why: attention is a finite resource. Spending it in proportion to the blast radius is what separates a useful review from a uniform, shallow one.

  3. Check out the branch and run it

    For anything non-trivial: gh pr checkout 1234, run it, exercise the critical path. Reading the diff on GitHub only shows what changed — not what the change does in the real system.

    Why: many bugs only surface at runtime (state, side effects, performance). The diff is a map, not the territory.

  4. Read the heart of the change first

    Identify the 2–3 files that carry the logic. Understand them deeply before the periphery (tests, config, renames). If the core is good, the rest follows; if it's bad, there's no point commenting on formatting.

    Why: commenting on the details of a design that's about to be reworked wholesale wastes your time and the author's.

  5. Read tests as a specification

    Do the tests describe the expected behavior, including edge and failure cases? A passing test proves nothing if it tests the wrong thing. Look for what isn't tested as much as what is.

    Why: tests are the safety net protecting future maintainers. Their quality predicts the code's healthy lifespan better than the code itself.

  6. Actively look for what could break

    Adopt the adversarial stance: null/empty inputs, concurrency, network failures, backward compatibility, effects on existing callers. Assume "this code is wrong" and try to prove it.

    Why: confirming that something "looks fine" is easy and misleading. Actively trying to break it is the only reliable way to find real defects.

  7. Synthesize, prioritize, phrase it

    Before writing, rank your remarks (see the ladder below). Clearly separate what blocks from what's a suggestion. End with a clear verdict: approve / request changes / needs discussion.

    Why: an unranked flood of comments drowns the critical signal. The author should know in 10 seconds what they must do.

02

The priority ladder

Not every comment carries the same weight. Labeling each remark — mentally and explicitly — keeps the spacing debate from burying the security flaw.

P1

Correctness & security

Bugs, races, vulnerabilities, data loss, regressions. Always blocking.

P2

Design & architecture

Wrong abstraction, coupling, debt that will cost dearly. Blocking if structural.

P3

Maintainability & readability

Naming, complexity, missing tests. Should fix; rarely blocking alone.

P4

Suggestions / alternatives

"We could also…" Optional, marked nit: or suggestion:.

P5

Automatable style

Formatting, imports. Don't comment by hand — hand it to tooling.

Golden rule

If a remark is automatable (P5), never make it by hand: configure the linter/formatter once and for all. Your brain should serve the P1s and P2s — the ones only a human can judge.

03

Tools & the git/github method

Pull and explore the PR locally

# Direct checkout of the PR (GitHub CLI)
gh pr checkout 1234

# See the PR diff without leaving the terminal
gh pr diff 1234

# Status, CI checks, and conversations
gh pr view 1234 --comments

Read the diff intelligently

The default diff mixes everything together. A few options change the game:

# Ignore whitespace changes (focus on the real change)
git diff -w main...HEAD

# Track a moved function instead of "all deleted / all added"
git diff --color-moved=zebra

# Word-level diff rather than line-level, useful for dense text
git diff --word-diff

# Understand a suspicious line's history: who, when, why
git log -L :functionName:path/file.js
git blame -L 40,60 path/file.js
Investigator's reflex

git blame + git log -L answer "why does this line exist?" Before asking an author to delete something that looks useless, check whether it's a fix for a long-forgotten bug.

On GitHub, in the interface

  • Review by "viewed"-marked file to avoid re-reading and to keep a clear sense of progress on large PRs.
  • Group your comments into a single "Start a review" rather than isolated comments: the author gets coherent feedback, not ten notifications.
  • Use code suggestions (```suggestion) for trivial fixes: the author applies them in one click, zero friction.
  • Insist on a clean history via squash merge or atomic commits: a readable diff starts with readable slicing.
  • Delegate everything mechanical to CI: lint, format, coverage, tests, security scan. You should never manually comment on what an automated check can block.

Reduce the load at the source

The best review is enabled by a good PR. Through a PULL_REQUEST_TEMPLATE.md, encourage a structured description (context, approach, how to test, risks) and small, focused PRs. A 200-line PR gets real feedback; a 2,000-line PR gets a "LGTM."

04

Sharpening your analysis

Review is a cognitive exercise. Here's how to train it rather than endure it.

Build a mental model before judging

Before critiquing, state in one sentence what the code is supposed to do. If you can't, the problem may be your understanding — or the code's clarity. Either way it's a signal, not a blocker to your review.

Read by hypotheses, not linearly

Rather than reading line after line, pose questions and hunt for their answers: "how does this code handle failure?", "what happens if this call runs concurrently?" You then read code the way you'd question a witness, which engages attention far better than passive reading.

Passive reading

"I'll read it all and I'll see"

Diffuse attention, you approve what "looks correct," you miss subtle defects because you weren't looking for them.

Hypothesis-driven reading

"What must it prove, and does it?"

Directed attention, every question has an answer to find, blind spots become visible.

Name your reviewer biases

  • Familiarity bias: you quickly approve the style that resembles yours, and over-criticize a different but valid one.
  • Authority bias: "X wrote it, so it must be fine" — seniors ship bugs too, sometimes subtler ones.
  • End-of-diff fatigue: rigor drops after the 10th file. Recognize it and take a break rather than rubber-stamping.
  • Anchoring on the first detail: an ugly variable name at the top of a file grabs attention at the expense of the flaw 200 lines below.
Learning loop

When a bug reaches production despite a review: go back to the PR. What could you have caught? Which question did you fail to ask? This personal retro, done 4–5 times, sharpens your acuity more than any article.

Work your "off-review" reading

Regularly reading good code you didn't write — well-kept open source, other teams' PRs — broadens your repertoire of patterns. The more ways you've seen a problem solved, the faster you spot the one that smells off.

05

Delivering feedback that lands

A technically correct but hurtful review fails: the code may improve, but the relationship and the team's velocity degrade. Tone is part of engineering.

Avoid

"Why did you do this?"

Implicit judgment, puts people on the defensive, shuts down the conversation.

Prefer

"What led you to this approach? I'd have tried X — what risk am I missing?"

Curiosity, puts the code (not the person) at the center, opens a dialogue.

  • Aim at the code, never the person: "this function does two things" rather than "you're mixing responsibilities."
  • Ask questions when you're not sure you understand: often the author has a reason you don't know.
  • Label the intensity: blocking:, suggestion:, nit:, question:. The author knows what to prioritize.
  • Justify the "why" of a request: feedback that explains the risk teaches; a curt order just irritates.
  • Call out the good too: an elegant design deserves a comment. It's honest, and it calibrates the team on what's valued.
  • For a disagreement that stalls in writing, go synchronous (call, pairing) and summarize the decision in the PR afterward.
06

The reference checklist

To keep in mind (not to run through mechanically — it's a memory aid, not a form).

Correctness

  • Does the code solve the stated problem, and only that one?
  • Edge cases handled: null/empty, overflow, concurrency, network errors?
  • Possible regression on existing callers or the public API?

Security & data

  • User input validated and escaped (injection, XSS)?
  • Authz checked in the right place, secrets kept out of the code?
  • Reversible migrations, no risk of data loss?

Design

  • Is the abstraction right — neither over- nor under-engineered?
  • Does the change create debt that will be expensive to repay?

Tests & maintainability

  • Do tests cover behavior, failures included? What's missing?
  • Will a newcomer understand this code in six months without context?

Reviewing other people's code as carefully as your own —
that's where a codebase's quality is won (or lost).
