00

Réviser, ce n'est pas chercher des fautes

Une review qui se contente de pointer des coquilles de style apporte la valeur d'un linter — autrement dit, presque rien, puisque le linter le fait gratuitement. La valeur d'un reviewer est ailleurs : comprendre l'intention, évaluer si le changement résout vraiment le problème, et anticiper ce qui cassera dans six mois.

Le réflexe à cultiver : avant de juger le « comment », reconstruire le « pourquoi ». Une PR est une hypothèse — « ce code résout ce besoin sans rien casser ». Votre travail est de tester cette hypothèse, pas de réécrire le code à la place de l'auteur.

Principe directeur

Vous approuvez une intention, une approche et une dette technique — pas seulement des lignes. Demandez-vous toujours : « si ce code me pète à la figure en prod dans trois mois, l'aurais-je vu venir ici ? »

01

Le process, pas-à-pas

Un ordre de lecture délibéré évite le piège classique : se noyer dans le premier fichier ouvert et perdre la vue d'ensemble. Procédez du contexte vers le détail.

  1. Lire la description avant le code

    Quel problème ? Quel ticket ? Quelle approche annoncée ? Si la description est vide ou floue, c'est déjà un retour de review à formuler — vous ne pouvez pas valider ce que vous ne comprenez pas.

    Pourquoi : sans intention claire, chaque ligne devient ambiguë. Vous jugez alors le code contre votre idée du besoin, source n°1 des reviews stériles.

  2. Cadrer la portée et le risque

    Combien de fichiers, quelles zones ? Touche-t-on à l'authz, aux migrations, aux paiements, à une API publique ? Un changement de 3 lignes dans la couche d'auth mérite plus d'attention que 300 lignes de tests. Calibrez votre effort sur le risque, pas sur le volume.

    Pourquoi : l'attention est une ressource finie. La dépenser proportionnellement au blast radius est ce qui sépare une review utile d'une review uniforme et superficielle.

  3. Récupérer la branche et la faire tourner

    Pour tout ce qui n'est pas trivial : gh pr checkout 1234, on lance, on exerce le chemin critique. Lire le diff sur GitHub ne montre que ce qui a changé — pas ce que le changement fait dans le système réel.

    Pourquoi : beaucoup de bugs ne sont visibles qu'à l'exécution (états, effets de bord, perf). Le diff est une carte, pas le territoire.

  4. Lire le cœur du changement d'abord

    Identifiez le ou les 2-3 fichiers qui portent la logique. Comprenez-les en profondeur avant les périphéries (tests, config, renommages). Si le cœur est bon, le reste suit ; s'il est mauvais, inutile de commenter la mise en forme.

    Pourquoi : commenter les détails d'un design qui va être revu de fond en comble gaspille votre temps et celui de l'auteur.

  5. Vérifier les tests comme une spécification

    Les tests décrivent-ils le comportement attendu, y compris les cas limites et d'échec ? Un test qui passe ne prouve rien s'il teste la mauvaise chose. Cherchez ce qui n'est pas testé autant que ce qui l'est.

    Pourquoi : le test est le filet qui protège les futurs mainteneurs. Sa qualité prédit la durée de vie saine du code mieux que le code lui-même.

  6. Chercher activement ce qui pourrait casser

    Adoptez la posture adverse : entrées nulles/vides, concurrence, erreurs réseau, rétrocompatibilité, effets sur les appelants existants. Posez l'hypothèse « ce code est faux » et tentez de la prouver.

    Pourquoi : confirmer que « ça a l'air bien » est facile et trompeur. Tenter de casser activement est la seule méthode fiable pour trouver les défauts réels.

  7. Synthétiser, prioriser, formuler

    Avant d'écrire, classez vos remarques (voir l'échelle ci-dessous). Distinguez clairement ce qui bloque de ce qui est une suggestion. Terminez par un verdict net : approuve / demande des changements / besoin d'en discuter.

    Pourquoi : un flot de commentaires non hiérarchisés noie le signal critique. L'auteur doit savoir en 10 secondes ce qu'il doit faire.

02

L'échelle de priorités

Tout commentaire n'a pas le même poids. Étiqueter mentalement (et explicitement) chaque remarque évite que le débat sur l'espacement n'enterre la faille de sécurité.

P1

Correctness & sécurité

Bugs, races, failles, perte de données, régression. Bloquant, toujours.

P2

Design & architecture

Mauvaise abstraction, couplage, dette qui se paiera cher. Bloquant si structurant.

P3

Maintenabilité & lisibilité

Nommage, complexité, tests manquants. À corriger, rarement bloquant seul.

P4

Suggestions / alternatives

« On pourrait aussi… ». Optionnel, marqué nit: ou suggestion:.

P5

Style automatisable

Formatage, imports. Ne le commentez pas à la main — déléguez à l'outillage.

Règle d'or

Si une remarque est automatisable (P5), ne la faites jamais à la main : configurez le linter/formatter une bonne fois. Votre cerveau doit servir aux P1 et P2, que seul un humain peut juger.

03

Outils & méthodo git/github

Récupérer et explorer la PR localement

# Checkout direct de la PR (GitHub CLI)
gh pr checkout 1234

# Voir le diff de la PR sans quitter le terminal
gh pr diff 1234

# Statut, checks CI, et conversations
gh pr view 1234 --comments

Lire le diff intelligemment

Le diff par défaut mélange tout. Quelques options changent la donne :

# Ignorer les changements d'espacement (focus sur le vrai changement)
git diff -w main...HEAD

# Suivre une fonction déplacée au lieu de voir "tout supprimé / tout ajouté"
git diff --color-moved=zebra

# Diff au niveau mot plutôt que ligne, utile sur du texte dense
git diff --word-diff

# Comprendre l'historique d'une ligne suspecte : qui, quand, pourquoi
git log -L :nomFonction:chemin/fichier.js
git blame -L 40,60 chemin/fichier.js
Réflexe d'enquêteur

git blame + git log -L répondent à « pourquoi cette ligne existe-t-elle ? ». Avant de demander à un auteur de supprimer quelque chose qui semble inutile, vérifiez s'il ne s'agit pas d'un correctif à un bug oublié.

Sur GitHub, dans l'interface

  • Reviewez par fichier marqué « viewed » pour ne pas relire deux fois et garder une progression claire sur les grosses PR.
  • Groupez vos commentaires en une seule review « Start a review » plutôt qu'en commentaires isolés : l'auteur reçoit un retour cohérent, pas dix notifications.
  • Utilisez les suggestions de code (```suggestion) pour les corrections triviales : l'auteur les applique en un clic, zéro friction.
  • Exigez un historique propre via squash merge ou des commits atomiques : un diff lisible commence par un découpage lisible.
  • Déléguez à la CI tout ce qui est mécanique : lint, format, coverage, tests, scan de sécu. Vous ne devriez jamais commenter manuellement ce qu'un check automatique peut bloquer.

Réduire la charge à la source

La meilleure review est facilitée par une bonne PR. Encouragez, via un PULL_REQUEST_TEMPLATE.md, une description structurée (contexte, approche, comment tester, risques) et des PR petites et ciblées. Une PR de 200 lignes reçoit un vrai retour ; une PR de 2000 lignes reçoit un « LGTM ».

04

Affûter sa capacité d'analyse

La review est un exercice cognitif. Voici comment l'entraîner plutôt que de le subir.

Construisez un modèle mental avant de juger

Avant de critiquer, formulez en une phrase ce que le code est censé faire. Si vous n'y arrivez pas, le problème est peut-être votre compréhension — ou la clarté du code. Dans les deux cas, c'est un signal, pas un blocage à votre review.

Lisez par hypothèses, pas linéairement

Plutôt que de lire ligne après ligne, posez des questions et cherchez leurs réponses : « comment ce code gère-t-il l'échec ? », « que se passe-t-il si cet appel est concurrent ? ». Vous lisez alors le code comme on interroge un témoin, ce qui mobilise l'attention bien mieux qu'une lecture passive.

Lecture passive

« Je lis tout et je verrai bien »

Attention diffuse, on valide ce qui « semble correct », on rate les défauts subtils car on ne les cherchait pas.

Lecture par hypothèses

« Que doit-il prouver, et le prouve-t-il ? »

Attention dirigée, chaque question a une réponse à trouver, les angles morts deviennent visibles.

Nommez vos biais de reviewer

  • Biais de familiarité : on valide vite le style qui ressemble au nôtre, on sur-critique le style différent mais valide.
  • Biais d'autorité : « c'est X qui l'a écrit, ça doit être bon » — les seniors écrivent aussi des bugs, parfois plus subtils.
  • Fatigue de fin de diff : la rigueur chute après le 10ᵉ fichier. Reconnaissez-le et faites une pause plutôt que de tamponner.
  • Ancrage sur le premier détail : un nom de variable moche en tête de fichier capte l'attention au détriment de la faille 200 lignes plus bas.
Boucle d'apprentissage

Quand un bug atteint la prod malgré une review : revenez à la PR. Qu'auriez-vous pu repérer ? Quelle question n'avez-vous pas posée ? Cette rétro personnelle, faite 4-5 fois, transforme plus votre acuité que n'importe quel article.

Travaillez votre lecture « hors review »

Lire régulièrement du bon code que vous n'avez pas écrit — bases open source soignées, PR d'autres équipes — élargit votre répertoire de patterns. Plus vous avez vu de manières de résoudre un problème, plus vite vous repérez celle qui sent mauvais.

05

Communiquer un retour qui passe

Une review techniquement juste mais blessante échoue : le code s'améliore peut-être, mais la relation et la vélocité de l'équipe se dégradent. Le ton fait partie de l'ingénierie.

À éviter

« Pourquoi tu fais ça ? »

Jugement implicite, met sur la défensive, ferme la discussion.

À privilégier

« Qu'est-ce qui t'a orienté vers cette approche ? J'aurais tenté X — quel risque je rate ? »

Curiosité, place le code (pas la personne) au centre, ouvre un échange.

  • Visez le code, jamais la personne : « cette fonction fait deux choses » plutôt que « tu mélanges les responsabilités ».
  • Posez des questions quand vous n'êtes pas sûr de comprendre : souvent l'auteur a une raison que vous ignorez.
  • Étiquetez l'intensité : blocking:, suggestion:, nit:, question:. L'auteur sait quoi prioriser.
  • Justifiez le « pourquoi » d'une demande : un retour qui explique le risque enseigne ; un ordre sec ne fait qu'agacer.
  • Soulignez aussi le bon : un design élégant mérite un commentaire. C'est honnête, et ça calibre l'équipe sur ce qui est valorisé.
  • Pour un désaccord qui s'enlise par écrit, passez en synchrone (appel, pairing) et résumez la décision dans la PR ensuite.
06

La checklist de référence

À garder en tête (pas à dérouler mécaniquement — c'est un aide-mémoire, pas un formulaire).

Correctness

  • Le code résout-il bien le problème décrit, et seulement celui-là ?
  • Cas limites gérés : null/vide, débordement, concurrence, erreurs réseau ?
  • Régression possible sur les appelants existants ou l'API publique ?

Sécurité & données

  • Entrées utilisateur validées et échappées (injection, XSS) ?
  • Authz vérifiée au bon endroit, secrets hors du code ?
  • Migrations réversibles, pas de risque de perte de données ?

Design

  • L'abstraction est-elle juste, ni sur- ni sous-conçue ?
  • Le changement crée-t-il une dette qui coûtera cher à rembourser ?

Tests & maintenabilité

  • Les tests couvrent-ils le comportement, échecs inclus ? Que manque-t-il ?
  • Un nouvel arrivant comprendra-t-il ce code dans six mois sans contexte ?

Réviser le code des autres aussi attentivement que le sien —
c'est là que se gagne (ou se perd) la qualité d'une base de code.
